# Releasing Lexora

This document describes how to cut a public release of Lexora end-to-end.

## Overview

Releases are driven by **annotated git tags** of the form `v<MAJOR>.<MINOR>.<PATCH>` (optionally with a pre-release suffix like `-rc.1`). Pushing such a tag triggers `.github/workflows/release-windows.yml`:

1. CI checks out the tag.
2. The workflow's `Resolve version` step parses the version from the tag.
3. `tauri.conf.json` and `apps/desktop/src-tauri/Cargo.toml` are rewritten in-place to match the tag — the version recorded in `main` does **not** need to be bumped manually.
4. The Tauri Windows bundler builds signed NSIS and MSI installers plus updater `.sig` files.
5. A second job downloads the artifacts, extracts the matching CHANGELOG section as release notes, and creates a **draft** GitHub Release.
6. A human reviewer toggles the draft to published once the artifacts have been smoke-tested.

The `workflow_dispatch` path still works for ad-hoc builds — it produces the artifacts but does not create a Release.

## Required repository configuration

The workflow expects these secrets and variables to be set on the GitHub repository:

| Name                                 | Kind     | Purpose                                                                                 |
| ------------------------------------ | -------- | --------------------------------------------------------------------------------------- |
| `TAURI_UPDATER_ENDPOINT`             | Variable | HTTPS URL of the updater feed (e.g. `https://releases.example.com/lexora/latest.json`). |
| `TAURI_UPDATER_PUBLIC_KEY`           | Variable | Public key generated by `tauri signer generate`.                                        |
| `TAURI_SIGNING_PRIVATE_KEY`          | Secret   | The matching private key — never commit this.                                           |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Secret   | Optional password for the private key if it was generated encrypted.                    |

The `Require updater signing key` step fails fast if any of these are missing.

## Cutting a release

1. Verify `main` is green locally:

   ```sh
   pnpm typecheck
   pnpm --filter desktop test
   cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml --lib
   pnpm test:e2e
   pnpm format:check
   ```

2. Move the `[Unreleased]` content in `CHANGELOG.md` under a new versioned heading and update the comparison links:

   ```markdown
   ## [Unreleased]

   _no entries yet_

   ## [0.1.1] — 2026-05-22

   ### Added

   - …

   [Unreleased]: …compare/v0.1.1...HEAD
   [0.1.1]: …releases/tag/v0.1.1
   ```

3. Commit, push, and tag:

   ```sh
   git commit -am "docs: prepare 0.1.1 release notes"
   git push
   git tag -a v0.1.1 -m "Lexora 0.1.1"
   git push origin v0.1.1
   ```

4. Watch the **Release Windows Installer** workflow run.

5. Review the draft Release on GitHub:
   - Confirm the version in the title matches the tag.
   - Confirm the installer and `.sig` files are attached.
   - Edit the auto-generated release notes if needed.
   - Publish the Release.

## Versioning policy

- **MAJOR** is reserved for breaking storage or IPC contract changes.
- **MINOR** is for additive features (new commands, new screens) — no breaking changes.
- **PATCH** is reserved for bug fixes and dependency bumps.
- Pre-releases use suffixes like `-rc.1`, `-beta.2`. The workflow auto-marks any tag containing a `-` as a `prerelease: true` in the GitHub Release.

## Hot-fix flow

For an urgent fix:

1. Branch off the latest release tag: `git checkout -b hotfix/0.1.2 v0.1.1`.
2. Apply the patch, commit, push the branch.
3. Tag from that branch: `git tag -a v0.1.2 -m "Lexora 0.1.2 hotfix"`.
4. Merge the branch back into `main` after the release lands.

## Rolling back a bad release

- If the draft has not been published yet, delete the draft and the tag (`git push --delete origin v0.1.2`, then locally `git tag -d v0.1.2`).
- If users have already installed a bad build, cut a new patch release that supersedes it and use the updater channel to push the fix.
